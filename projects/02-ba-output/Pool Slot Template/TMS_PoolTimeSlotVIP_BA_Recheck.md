## ส่วนที่ 1 — Business Requirement: Setup Config Time Slot (VIP) หน้า "แก้ไขข้อมูล Pool"
*(โดย ba1-business-analyst)*

### 1. Objective
จากไฟล์ดีไซน์และงานที่ได้รับ สรุปได้ว่าเป้าหมายคือ: ยืนยัน/ทำให้หน้า "แก้ไขข้อมูล Pool" รองรับการตั้งค่ารอบเวลาจัดส่ง (Time Slot) ที่แยกประเภท **Normal** และ **VIP** ได้อย่างสมบูรณ์ — เห็นได้จากแผงสรุปที่มีค่า "รอบ VIP" แยกจาก "รอบจัดส่งที่เปิดใช้งาน" โดยเฉพาะ

**⚠️ ยังไม่ทราบ objective เชิงธุรกิจที่แท้จริง** เช่น รอบ VIP แก้ pain point อะไร (ลูกค้าจ่ายเพิ่มเพื่อ slot พิเศษ? ลูกค้าเกรด VIP ได้สิทธิ์จองก่อน? ทีมปฏิบัติการต้องการแยกคิว?) — ไม่ปรากฏในไฟล์ดีไซน์ ต้องถาม PO (ดูข้อ 12)

### 2. User / Actor
- **Admin/CFW** (พบใน header ดีไซน์: "คุณ CFW AdminBangna" สังกัด "เซ็นทรัล ฟู้ด โฮลเซลส์ บจ. (สาขาบางนา)") เป็นผู้เข้าใช้หน้านี้เพื่อแก้ไขข้อมูล Pool
- **⚠️ ยังไม่ทราบ** ว่ามี Role อื่นที่เข้าหน้านี้ได้อีกหรือไม่ (เช่น Central IT/Ops ส่วนกลาง) และแต่ละ Role มีสิทธิ์ แก้ไข/ดูอย่างเดียว/อนุมัติ ต่างกันหรือไม่ — เมนู "ข้อมูลกำหนดสิทธิ์ Pool และโซนจัดส่ง" ที่อยู่ใน sidebar เดียวกันน่าจะเกี่ยวข้อง แต่ยังไม่ได้รับรายละเอียด

### 3. Business Flow (As-is → To-be)
**As-is:** ไม่ทราบแน่ชัด — ไฟล์ดีไซน์ที่ได้รับแสดงหน้าจอที่มีข้อมูลจริงอยู่แล้ว (Pool P0230, มีรอบเวลาจัดส่ง 10 รายการ ทั้ง Normal/VIP) จึงสันนิษฐานว่าฟีเจอร์จัดการ Pool **มีอยู่แล้วในระบบ**, งานนี้น่าจะเป็นการต่อเติม/ยืนยัน spec ให้รองรับ VIP ให้ครบ ไม่ใช่สร้างฟีเจอร์ใหม่ทั้งหมด — **ต้องยืนยันกับ PO** ว่า As-is จริงคืออะไร (มีหน้านี้อยู่แล้วแต่ยังไม่รองรับ VIP type / หรือมีอยู่แล้วรองรับครบแต่ต้องการปรับจุดอื่น / หรือเป็นหน้าใหม่ทั้งหมด)

**To-be:** ผู้ใช้เปิดหน้า "แก้ไขข้อมูล Pool" → แก้ไขสถานะ/ชื่อ Pool และจัดการรอบเวลาจัดส่ง (เพิ่ม/แก้ไข/ลบ/เปิดปิดสถานะ) → **แก้ไขข้อมูลทั้งหมดที่ฝั่ง Frontend ก่อน** → กด "บันทึก" ครั้งเดียวเพื่อส่งข้อมูลทั้งหมดเข้า Backend พร้อมกัน (**ยืนยันแล้วจาก PO เมื่อ 10 ก.ย. 2569**: การเปิด/ปิดสถานะรายรอบ (Toggle) ไม่ commit ทันที ต้องรอกด "บันทึก" รวม)

### 4. Trigger & Condition / Exception
- Trigger เริ่ม flow: ผู้ใช้คลิก "แก้ไข" จากหน้ารายการ Pool
- Exception ที่พบในดีไซน์: มีปุ่ม "ย้อนกลับ" ให้ออกจากหน้าโดยไม่บันทึก — **ยังไม่ทราบ** ว่าต้องมีการแจ้งเตือนก่อนออกหากมีข้อมูลค้างที่ยังไม่บันทึก (รวมถึงการ Toggle สถานะรอบที่เพิ่งยืนยันว่าต้อง "รอบันทึก") หรือปล่อยให้ออกได้เลยโดยละทิ้งการเปลี่ยนแปลง
- **ยังไม่ทราบ** เงื่อนไข exception เมื่อบันทึกไม่สำเร็จ (เช่น Capacity เกิน, เวลาทับซ้อน) — ควร reset การ toggle กลับไปสถานะเดิมหรือคงค้างให้ผู้ใช้แก้ไขต่อ

### 5. ข้อมูลที่เกี่ยวข้อง
- ข้อมูล Pool: รหัส (read-only), ชื่อไทย/อังกฤษ, สถานะการใช้งาน
- ข้อมูลรอบเวลาจัดส่ง (ต่อ Pool): ช่องทางการจัดส่ง (Delivery/Pickup), ช่องทางการขาย (SD/WA/XB/XC), Slot Type (Normal/VIP), Truck Turn, เวลาเริ่มต้น/สิ้นสุด, Duration, Capacity, Cut Off Time, สถานะ
- ข้อมูลสรุปที่คำนวณ: Capacity รวม, จำนวนช่องทางการขายที่เปิดใช้งาน, จำนวนรอบจัดส่งที่เปิดใช้งาน, จำนวนรอบ VIP

### 6. Business Rule
1. รหัส Pool แก้ไขไม่ได้ (read-only)
2. ชื่อ Pool ไทย/อังกฤษ บังคับกรอก
3. Slot Type มี 2 ค่า Normal/VIP เท่านั้น (เท่าที่เห็นในดีไซน์ — **ยังไม่ทราบ** ว่าจะมีประเภทอื่นเพิ่มในอนาคตหรือไม่)
4. **การแก้ไขทุกอย่างในหน้านี้ (รวม Toggle สถานะรอบ) ต้อง commit ผ่านปุ่ม "บันทึก" เพียงจุดเดียว — ไม่มีจุดไหนใน UI ที่ save ทันทีแยกจากปุ่มนี้** (ยืนยันจาก PO)
5. ต้องมี Modal ยืนยันก่อนลบรอบเวลาจัดส่งเสมอ
6. **ยังไม่ทราบ**: เงื่อนไขปิดสถานะ Pool เมื่อยังมีรอบเวลาจัดส่งเปิดอยู่, ขอบเขตความสัมพันธ์ Capacity รวมของ Pool กับผลรวม Capacity รายรอบ (บังคับเป๊ะ หรือแค่ warning)

### 7. Success Criteria
**ยังไม่ได้รับจาก PO** — ต้องถามว่างานนี้ถือว่า "เสร็จ" เมื่อใด เช่น: ผู้ใช้ตั้งค่ารอบ VIP ได้ครบตามที่ต้องการ / ไม่มี Capacity เกินหลุดออกไปยังระบบรับออเดอร์ / เวลาตอบสนองของหน้าจอ ฯลฯ (ดูข้อ 12)

### 8. Out of Scope
- หน้าจอ ข้อมูลโซนจัดส่ง, ข้อมูลโควต้า Pool, ข้อมูลกำหนดสิทธิ์ Pool และโซนจัดส่ง (อยู่ใน sidebar กลุ่มเดียวกันแต่เป็นเมนูแยก)
- การสร้าง Pool ใหม่ (หน้านี้เป็นหน้า "แก้ไข" เท่านั้น รหัส Pool เป็น read-only)

### 9. Dependency
- ขึ้นกับ Master data: ช่องทางการจัดส่ง, ช่องทางการขาย, ประเภท Slot, ค่า Truck Turn ที่ใช้ได้ของแต่ละ Pool
- อาจกระทบ/เชื่อมกับ "ระบบจัดเส้นทาง" และ "ประวัติการสั่งซื้อสินค้า" (เมนูในระบบเดียวกัน) เนื่องจากรอบเวลาจัดส่งที่ตั้งค่าที่นี่น่าจะถูกใช้อ้างอิงตอนลูกค้าเลือก slot สั่งซื้อ — **ยังไม่ยืนยันจุดเชื่อมต่อจริง**

### 10. ⚠️ Concern ที่ต้องแจ้ง PO
- ยังไม่มี objective/Success Criteria เชิงธุรกิจที่ชัดเจน (ข้อ 1, 7) — เสี่ยงต่อการตีความ scope ผิดถ้าปล่อยไว้
- ไม่มีดีไซน์ของ Modal "เพิ่ม/แก้ไขรอบเวลาจัดส่ง" และ Modal ยืนยันการลบแนบมาด้วย — field ที่ใช้อยู่ในเอกสารเป็นการอนุมานจากคอลัมน์ตารางเท่านั้น
- Permission/สิทธิ์ผู้ใช้งานต่อหน้านี้ยังไม่ชัดเจน (ข้อ 2) — มีผลต่อทั้ง UX (ซ่อน/แสดงปุ่ม) และ Backend (authorization check)

### 11. 🔧 จุดสังเกตสำหรับ BA เทคนิค (เบื้องต้น ยังไม่ใช่ design)
- Business Rule ข้อ 4 (บันทึกรวมจุดเดียว รวมถึง Toggle) มีผลโดยตรงต่อการออกแบบ state ฝั่ง Frontend: ต้องมี "pending change" state แยกจาก state ที่ยืนยันแล้ว จนกว่าจะบันทึกสำเร็จ
- น่าจะต้องมี logic ฝั่ง backend ตรวจสอบ **ผลรวม Capacity** และ **Truck Turn ซ้ำ/เวลาทับซ้อน** มากกว่า 1 ชั้น (ตอนสร้าง/แก้ไขรอบเดี่ยว และตอนบันทึกรวมทั้งฟอร์ม)
- จุดที่ต้องเช็คสิทธิ์ตาม role (รอผล PO ข้อ 2/9) — ยังไม่ทราบว่ามีกี่ role
- น่าจะต้องมี API เชื่อมกับ "ระบบจัดเส้นทาง"/"ระบบรับออเดอร์" เพื่อให้ slot ที่ตั้งค่าที่นี่ถูกใช้จริง — ยังไม่ทราบทิศทางการเชื่อม (หน้านี้ push ข้อมูล หรือระบบอื่น pull ข้อมูล)
- สถานะของรอบเวลาจัดส่ง (เปิด/ปิด) อาจต้องออกแบบเป็น state ที่มีมากกว่า boolean ในอนาคต (เช่น "ปิดชั่วคราวเนื่องจากเต็ม") — ปัจจุบันดีไซน์มีแค่ เปิด/ปิด

### 12. ❓ ข้อมูลที่ยังขาด — ต้องการคำตอบจาก PO ก่อนไปต่อ
1. Objective เชิงธุรกิจของรอบ VIP คืออะไร (ข้อ 1)
2. มี Role ใดบ้างเข้าหน้านี้ได้ และสิทธิ์ต่างกันอย่างไร (ข้อ 2)
3. As-is ของหน้านี้คืออะไรกันแน่ — มีอยู่แล้วบางส่วน หรือสร้างใหม่ทั้งหมด (ข้อ 3)
4. เมื่อออกจากหน้าโดยมีข้อมูลค้าง (รวม Toggle ที่ยังไม่บันทึก) ต้องมี prompt เตือนหรือไม่ (ข้อ 4)
5. ปิดสถานะ Pool ได้เสมอ หรือมีเงื่อนไขบล็อกเมื่อมีรอบเปิดอยู่ (ข้อ 6)
6. Success Criteria ของงานนี้คืออะไร (ข้อ 7)
7. หน้านี้เชื่อมกับระบบจัดเส้นทาง/รับออเดอร์อย่างไร (ข้อ 9)

## ส่วนที่ 2 — Technical Analysis: Setup Config Time Slot (VIP) หน้า "แก้ไขข้อมูล Pool"
*(โดย ba2-tech-analyst — รับช่วงต่อจาก BRD ด้านบน)*

### 1. Technical Flow / State ของข้อมูล

```
โหลดข้อมูล Pool + รอบเวลาจัดส่ง (server state)
    → ผู้ใช้แก้ไขฟอร์ม Pool / เพิ่ม-แก้ไข-ลบ-toggle รอบเวลาจัดส่ง (เก็บใน "draft/pending state" ฝั่ง Frontend เท่านั้น)
    → กด "บันทึก" → validate ทั้งหมด (client-side ก่อน, server-side ซ้ำ)
        → ผ่าน → commit "draft state" → server state (transaction เดียว) → กลับหน้ารายการ
        → ไม่ผ่าน → แสดง error, "draft state" ยังคงอยู่ให้แก้ไขต่อ
    → กด "ย้อนกลับ" → ละทิ้ง "draft state" ทั้งหมด → กลับหน้ารายการ
```

สถานะรอบเวลาจัดส่งแต่ละแถวควรมี 2 สถานะซ้อนกันฝั่ง Frontend: `savedIsActive` (ค่าจาก server) และ `draftIsActive` (ค่าที่ผู้ใช้กำลังแก้) — ส่วนต่างระหว่างสองค่านี้คือสิ่งที่ต้องส่งใน payload ตอนบันทึก และเป็นตัวกำหนดว่าจะ highlight แถวว่า "แก้ไขแล้วยังไม่บันทึก" หรือไม่

### 2. Frontend Requirement

| หน้าจอ | Role ที่เห็น | Field/Element หลัก | Interaction |
|---|---|---|---|
| แก้ไขข้อมูล Pool (หน้าหลัก) | Admin/CFW (role อื่นรอยืนยันจาก PO) | Toggle สถานะ Pool, รหัส Pool (read-only), ชื่อ Pool TH/EN, แผงสรุป 4 ค่า | แก้ไขฟอร์ม, กด บันทึก/ย้อนกลับ พร้อม prompt แจ้งเตือน unsaved changes (รอยืนยัน PO) |
| ตารางรอบเวลาจัดส่ง (ในหน้าเดียวกัน) | เดียวกับข้างต้น | 11 คอลัมน์ตามดีไซน์ + ปุ่ม "เพิ่มเวลารอบจัดส่ง" + Pagination (5/10/20/50) | Toggle เปลี่ยนเฉพาะ draft state ไม่ยิง API ทันที (ตาม BRD ข้อ 4), คลิกไอคอนแก้ไข/ลบเปิด Modal ที่เกี่ยวข้อง |
| Modal เพิ่ม/แก้ไขรอบเวลาจัดส่ง | เดียวกับข้างต้น | ฟอร์มตามคอลัมน์ตาราง (ยังไม่มีดีไซน์จริง — รอ UX) | บันทึกใน Modal นี้จะเพิ่ม/แก้ draft state ของตาราง ไม่ได้ยิง API ทันทีเช่นกัน เพื่อให้สอดคล้องกับ Journey "บันทึกรวมจุดเดียว" — **ต้องยืนยันกับ PO ว่า Add/Edit ผ่าน Modal นี้ commit ทันทีหรือรอบันทึกรวมด้วยเช่นกัน** (ยังไม่ชัดจาก scope เดิม) |
| Modal ยืนยันการลบ | เดียวกับข้างต้น | ข้อความยืนยัน + ปุ่มยืนยัน/ยกเลิก | ยืนยันแล้ว = ลบออกจาก draft state (หรือยิง DELETE ทันที — ขึ้นกับผลข้อข้างต้น) |

### 3. API / Backend Logic (Overview)

| Action | Endpoint แนะนำ | Business Logic ที่ต้องมี | Data ที่เกี่ยวข้อง |
|---|---|---|---|
| โหลดข้อมูลหน้า | ดึง Pool detail + รายการรอบเวลาจัดส่ง | permission check ตาม role, คำนวณค่าสรุป 4 ค่า | Pool, TimeSlot[] |
| บันทึกข้อมูล Pool (ปุ่ม บันทึก) | จุดเดียวที่เขียนข้อมูลจริง | รับ diff ของรอบเวลาจัดส่งที่ toggle เปลี่ยน (`timeSlotStatusUpdates[]`) พร้อมข้อมูล Pool หลัก, ประมวลผลเป็น transaction เดียว, validate ผลรวม Capacity + เงื่อนไขปิดสถานะ Pool ก่อน commit | Pool, TimeSlot[] (status only) |
| เพิ่ม/แก้ไขรอบเวลาจัดส่งเดี่ยว | ตาม Modal เพิ่ม/แก้ไข | validate Truck Turn ซ้ำ/เวลาทับซ้อน, ฟิลด์บังคับ — **ต้องยืนยันว่ายิงทันทีตอนปิด Modal หรือ commit พร้อมปุ่มบันทึกหลัก** | TimeSlot |
| ลบรอบเวลาจัดส่ง | ตาม Modal ยืนยันลบ | ต้องผ่าน confirm ก่อนเสมอ | TimeSlot |

**Error / Edge Case ที่ต้องรองรับ:**
- บันทึกไม่สำเร็จ (validation fail ฝั่ง server) — draft state ฝั่ง Frontend ต้องไม่หาย ต้องแสดง error ให้ผู้ใช้แก้ไขต่อได้
- ผู้ใช้ toggle สถานะรอบหลายแถว แล้วบันทึกพร้อมกัน แต่บางแถวชนกับ business rule (เช่น เปิดรอบทำให้ Capacity รวมเกิน) — ต้องระบุได้ว่า "แถวไหน" ที่ error ไม่ใช่ error รวมทั้งฟอร์ม
- ผู้ใช้เปิดหน้าเดียวกันจากสองแท็บ/สองคนพร้อมกัน แล้วบันทึกชนกัน (concurrent edit) — ยังไม่มีข้อมูลว่าระบบต้องรองรับหรือไม่

**จุดเชื่อมต่อระบบภายนอก (ถ้ามี):**
- เป็นไปได้ว่าต้องเชื่อมกับ "ระบบจัดเส้นทาง"/ระบบรับออเดอร์ เพื่อให้ slot ที่ตั้งค่าที่นี่ถูกใช้จริง — ยังไม่ยืนยันทิศทาง/รูปแบบการเชื่อมต่อ (ตาม BRD ข้อ 12.7)

### 4. Acceptance Criteria (สำหรับ QA)

- **Given** ผู้ใช้เปิดหน้า "แก้ไขข้อมูล Pool" และ **When** คลิก Toggle เปลี่ยนสถานะของรอบเวลาจัดส่งหนึ่งแถว **Then** ระบบต้อง **ไม่** ยิง network request ใด ๆ ทันที และต้องแสดงว่าแถวนั้นมีการแก้ไขที่ยังไม่บันทึก
- **Given** ผู้ใช้ toggle สถานะหลายแถวแล้วกด "บันทึก" **When** การบันทึกสำเร็จ **Then** ทุกแถวที่ toggle ต้องถูกอัปเดตสถานะจริงในระบบภายในคำขอเดียว (ไม่ใช่หลายคำขอแยกต่อแถว)
- **Given** ผู้ใช้ toggle สถานะรอบแล้ว **When** กด "ย้อนกลับ" โดยยังไม่กด "บันทึก" **Then** สถานะของรอบต้องกลับไปเป็นค่าเดิมตามระบบ ไม่มีการเปลี่ยนแปลงเกิดขึ้นจริง
- **Given** ผลรวม Capacity ของรอบที่จะ "เปิด" หลังบันทึกเกิน Capacity รวมของ Pool **When** กด "บันทึก" **Then** ระบบต้อง reject การบันทึกพร้อมระบุแถว/สาเหตุที่ error ชัดเจน และค่าที่ผู้ใช้แก้ไขต้องไม่หาย
- **Given** มี 2 รอบเวลาจัดส่งที่ Truck Turn เดียวกันและช่วงเวลาทับซ้อนกัน **When** พยายามบันทึก (ไม่ว่าจะสร้างใหม่หรือแก้ไข) **Then** ระบบต้อง reject พร้อมข้อความระบุคู่ที่ชนกัน
- **Given** ผู้ใช้กดลบรอบเวลาจัดส่ง **When** ยังไม่กดยืนยันใน Modal **Then** รอบนั้นต้องยังคงอยู่ในระบบ

### 5. 📌 จุดที่ UX Designer ต้องรู้ก่อนทำ Screen Flow
- ต้องออกแบบ **สถานะ "แก้ไขแล้วยังไม่บันทึก"** ให้มองเห็นชัดในตาราง (เช่น highlight แถว/ไอคอน) เนื่องจากผู้ใช้แก้ไขได้หลายจุด (toggle, เพิ่ม, แก้ไข, ลบ) ก่อนจะบันทึกจริงครั้งเดียว
- ต้องออกแบบ prompt แจ้งเตือนก่อนออกจากหน้าเมื่อมี unsaved changes (รอยืนยัน PO ว่าต้องมีหรือไม่)
- ต้องออกแบบ error state ที่ระบุได้เป็นรายแถว ไม่ใช่ error message รวมทั้งฟอร์ม (จากข้อ 3 Error case)
- ยังไม่มีดีไซน์ของ Modal เพิ่ม/แก้ไขรอบเวลาจัดส่ง และ Modal ยืนยันลบ — เป็นงานที่ UX ต้องออกแบบใหม่

### 6. ❓ ข้อมูลที่ยังขาด/ไม่ชัดเจน
- Add/Edit รอบเวลาจัดส่งผ่าน Modal commit ทันทีหรือรอบันทึกรวม (Frontend Requirement ตาราง แถว Modal เพิ่ม/แก้ไข)
- ระบบต้องรองรับ concurrent edit (สองคนแก้ Pool เดียวกันพร้อมกัน) หรือไม่
- ทุกข้อจาก BRD ส่วนที่ 1 ข้อ 12 ที่ยังไม่ได้รับคำตอบจาก PO
