### ผลสรุปสั้น
- **สูตร Utilization = Usage / Setup (เก็บเป็น ratio ไม่ ×100)** : ตรวจสอบด้วยการเปิดค่าจริง (`Value2`) เทียบ `NumberFormat` แล้ว **สอดคล้องกัน** ทั้งไฟล์ output ของ TMS PROC และไฟล์ตัวอย่างของ CFW เอง (ดูข้อ 3.10) — แม้ข้อความกำกับใน "Report Example" จะเขียนว่า "×100" ก็ตาม
- **จำนวนเชิงตัวเลข (Set Up / Usage) ระหว่างไฟล์ TMS PROC output กับ CFW Delivery ไม่ตรงกันในบางสาขา** ขณะที่ Usage เหมือนกันทุกแถวที่สุ่มตรวจ — **PO ยืนยันแล้วว่าการสรุปจุดนี้ต้อง query DB จริงเท่านั้น จะสรุปจาก Report ต้นฉบับของ CFW เพียงอย่างเดียวไม่ได้** (ดูข้อ 3.1 — ความเสี่ยง **High**, มีร่าง SQL query ให้ DBA รันต่อในภาคผนวก ข้อ 9)
- พบ **7 ประเด็น High**, **6 ประเด็น Medium**, **5 ประเด็น Low/ยืนยันแล้วว่าสอดคล้อง**, **3 ประเด็นที่ PO ยืนยันปิดแล้ว (ไม่ใช่ปัญหา/ไม่ต้องแสดงผล)** รวม **21 ข้อ** ในหมวด Checklist (ข้อ 3.1–3.21 หลังอัปเดตรอบนี้เพิ่มข้อ 3.21 เรื่อง Share Slot)
- **ไม่มีไฟล์ TMS PROC output ฝั่ง Pickup (`@DeliveryOptionCode='PIC'`)** ให้เทียบกับ CFW Pickup โดยตรง — เทียบได้เฉพาะฝั่ง Delivery แบบ cell-to-cell เท่านั้น
- **[อัปเดตจาก PO 2026-09-14]** PO ยืนยันแล้ว 3 ประเด็น: (1) VIP เป็น **Cap รวม** ไม่มี Sale Source มากับมัน (ข้อ 3.11/6.4), (2) "SD" คือ Sale Source ใหม่จริงตามระบบ ไม่ใช่ "STS" ที่ comment เก่าเขียนผิด (ข้อ 3.6/6.7), (3) ไม่ต้องแสดง `StoreCountInPool` ในรายงาน (ข้อ 3.18) — และมีคำถามใหม่เรื่อง **Usage>100% กับกรณี Share Slot ระหว่างสาขา** ซึ่งวิเคราะห์แล้วในข้อ 3.21 (สรุป: กรณีที่พบจริงในข้อ 3.5 มาจาก VIP fallback ไม่เกี่ยวกับ pool sharing แต่ SQL logic เพียงอย่างเดียวยัง **ฟันธงไม่ได้ 100%** ว่า pool sharing จะไม่มีวันทำให้ Usage>SetUp ต่อแถว — ดูรายละเอียดและสิ่งที่ต้องใช้ยืนยันเพิ่มในข้อ 3.21)

## 4. ⚠️ Concern ที่ต้องแจ้ง PO

- **ตัวเลข Set Up (capacity) ไม่ตรงกันระหว่าง TMS PROC output กับ CFW Delivery ในบางสาขา (Store 00006/รังสิต)** ขณะที่ Usage ตรงกันทุกแถวที่สุ่มตรวจ — สะท้อนว่าไฟล์ทั้งสองอาจถูกสร้างจาก snapshot ของ `C_PoolSlotTemplate` คนละเวลา/คนละ environment **[อัปเดต] PO ยืนยันแล้วว่าจุดนี้ต้องสรุปด้วยการ query database จริงเท่านั้น** ไม่ใช่การเทียบไฟล์ export ต่อไฟล์ export — มีร่าง query ให้ DBA รันต่อในภาคผนวก ข้อ 9.B (ข้อ 3.1, 3.3, 3.20)
- **ไม่มีไฟล์ตัวอย่างผลลัพธ์จาก TMS PROC ฝั่ง Pickup (`@DeliveryOptionCode='PIC'`)** จึงตรวจสอบความสอดคล้องกับ `Result_..._Pickup.xlsx` ของ CFW ได้แค่ระดับโครงสร้างคอลัมน์ ยังเทียบตัวเลขจริงไม่ได้ (ข้อ 3.8)
- **Utilization ที่เกิน 100% เป็นพฤติกรรมจริงของระบบ** (ไม่ใช่บั๊ก) จากกรณี VIP fallback เข้ากิน slot ที่ไม่มี capacity เผื่อไว้ — ต้องให้ CFW ยืนยันว่ายอมรับการแสดงผลแบบนี้ (ข้อ 3.5) **[อัปเดต] จากการวิเคราะห์เพิ่มเติม (ข้อ 3.21) กรณี >100% ที่เจอจริงมาจาก VIP fallback ในสาขาเดียวกัน ไม่เกี่ยวกับการแชร์ slot ข้าม Pool** แต่ SQL logic เพียงอย่างเดียวยัง **ฟันธงไม่ได้ 100%** ว่ากรณี pool sharing (StoreCountInPool>1) จะไม่มีวันทำให้ Usage>SetUp เช่นกัน — ต้องดูเคสข้อมูลจริงหรือโค้ด booking engine เพิ่มเพื่อยืนยันขาด (ดูข้อ 3.21)
- **[ใหม่] พบความเสี่ยงกลับด้านจากกรณี Pool sharing**: เพราะ Set Up ถูกคำนวณระดับ Pool แล้ว "ซ้ำเต็มจำนวน" ให้ทุกสาขาในพูล (ไม่ได้หารตามสัดส่วน) ถ้าหลายสาขาในพูลเดียวกันรวมกันจองเกิน capacity จริงของพูล แต่ละแถวอาจยังโชว์ Utilization ต่ำกว่า 100% ทั้งที่พูลจริงถูกใช้เกินแล้ว — คือความเสี่ยง "under-report" ที่ตรงข้ามกับคำถามเดิมเรื่อง Usage>100% (ดูข้อ 3.21 และ 3.12)

## 5. 🔧 จุดสังเกตสำหรับ BA เทคนิค (เบื้องต้น)

- **[ยืนยันแล้วจาก PO — CR เพิ่มการแสดงผล VIP]** VIP เป็น **field "Cap รวม" ก้อนเดียว ไม่มี Sale Source/channel breakdown มากับมัน** — ตอนออกแบบ API/data model **ห้ามพยายามแตก VIP ตาม channel** (SD/WA/XB/XC) เพราะไม่มีข้อมูลนั้นจริง ให้ map เป็น field แยกต่างหาก 1 ก้อน (ตรงกับ PROC: `ColumnKey='VIP'` ไม่แตกราย channel, SQL บรรทัด 322–328) และ `Total = SUM(channel ปกติ) + VIP` เสมอ (Assumption C) — แนะนำให้มี test case ที่ channel ปกติและ VIP ไม่เป็นศูนย์พร้อมกันตอน UAT เพื่อยืนยัน arithmetic (ข้อ 3.11)
- จุดที่ต้องมี validation/state เพิ่ม: แถวที่ **Set Up ว่าง + Usage > 0** (`IsMissingSetup=1`) ควรมี field/flag แยกให้ frontend ใช้แสดงผลต่างจากแถวปกติ ไม่ใช่พึ่ง Utilization="0.00%" เพียงอย่างเดียว (ข้อ 3.4)
- Utilization ที่เกิน 100% ต้องคิดเรื่อง UI/format ล่วงหน้า (ไม่ควร cap หรือ error) — เป็นค่าที่ backend คำนวณถูกต้องตามนิยาม engine กรณีที่ยืนยันแล้วเกิดจาก VIP fallback ในสาขาเดียวกัน (ข้อ 3.5, 3.21)
- Business rule การแยก Delivery/Pickup ที่ระดับคอลัมน์ (SD/VIP มีเฉพาะบาง DeliveryOptionCode หรือไม่) ต้องเช็คให้ชัดก่อนออกแบบ API ว่าโครงสร้างคอลัมน์เป็น dynamic ตามข้อมูลจริง หรือ fix ตาม business rule (ข้อ 3.7)
- **[ปรับตาม PO]** ไม่ต้องมี field/badge `StoreCountInPool` ในรายงานที่ผู้ใช้เห็น (PO ยืนยันแล้ว, ข้อ 3.18) — แต่ backend ยังควร**เก็บ awareness เรื่อง Pool sharing ไว้ในใจตอนออกแบบ** เพราะ Set Up ระดับสาขาที่อยู่ Pool เดียวกันเป็นตัวเลขซ้ำ (ไม่ใช่ exclusive capacity) ถ้าในอนาคตต้องรวม/เปรียบเทียบ Utilization ข้ามสาขา ต้องระวังไม่เอา Set Up ของสาขาในพูลเดียวกันมาบวกกันตรงๆ (จะเกิด double count) — ดูความเสี่ยง under-report ที่เกี่ยวข้องในข้อ 3.21
- Field `IsCreateJob` filter (เปิด/ปิด) เป็น business decision ที่ยังไม่ปิด — กระทบ Usage ทุกแถวถ้าเปลี่ยน ควรรอ BA ยืนยันก่อนแตก API (ข้อ 3.14)
- **[ใหม่]** เรื่อง "Usage>100% กับ Pool sharing" (คำถาม PO, ข้อ 3.21): ยืนยันได้ว่ากรณีจริงที่เจอมาจาก VIP fallback ไม่ใช่ pool sharing แต่ตัว PROC/SQL **ไม่มีกลไกป้องกัน** ไม่ให้สาขาหนึ่งในพูลที่แชร์กัน Usage เกิน SetUp ที่แสดง (การป้องกันถ้ามีอยู่ที่ฝั่ง booking engine ซึ่งอยู่นอกไฟล์ SQL ชุดนี้) — BA เทคนิคควรสอบถามทีม backend/booking engine เพิ่มก่อนออกแบบ validation ฝั่ง API ว่าต้อง handle เคสนี้หรือไม่

## 8. ✅ Acceptance Criteria — สำหรับ Case ความเสี่ยงสูง (High)

> **[ปรับแนวทางตาม PO 2026-09-15]** ครอบคลุมเฉพาะข้อที่สถานะ **High** ในหมวด 3 ปัจจุบัน (3.1, 3.3, 3.4, 3.5, 3.7, 3.8, 3.20, 3.21) — **เกณฑ์ผ่าน/ไม่ผ่านหลักคือการเทียบผลลัพธ์ของ PROC กับข้อมูลดิบใน Database โดยตรง** (`C_PoolSlotTemplate`, `D_BookingLog`, `M_Place`, `M_Pool`, `M_ChannelOfSell`) **ไม่ใช้ไฟล์ CFW (`Result_*.xlsx`) เป็นเกณฑ์ตัดสิน pass/fail อีกต่อไป** — ไฟล์ CFW ลดบทบาทเหลือแค่ข้อมูลอ้างอิงประกอบ/ประวัติศาสตร์ (ดูเชิงอรรถท้ายแต่ละ AC ที่อ้างถึง) โฟกัสของทุก AC คือ "PROC ดึงข้อมูลจาก source table ถูกต้องหรือไม่ มีเคสไหนที่ควรถูกดึงมาแต่หลุดหายไปจากรายงานบ้าง" ทุกข้อแบ่งเป็น **Happy Case** (ข้อมูลปกติ ไม่มี NULL/collision) และ **Unhappy Case** (edge case ที่นับจำนวนแถว "หลุด" ได้จริงจาก DB) เสมอ — **ยังไม่ได้ execute query ใดๆ ในรอบนี้** (ไม่มี DB connection ในเซสชันนี้) query ที่อ้างถึงภาคผนวก ข้อ 9 (9.A/9.B) คือของเดิมที่ปรับใช้ต่อได้ ส่วนที่เป็น query ใหม่จะเขียนกำกับไว้ในแต่ละ AC โดยตรง

### AC สำหรับข้อ 3.1 — Set Up (Capacity) ที่ PROC คำนวณ ต้องตรงกับ `C_PoolSlotTemplate` ใน DB

**Happy Case — template ปกติ (Capacity ไม่ NULL, ChannelCode ตรงกับ `M_ChannelOfSell` ที่ Active)**
- **Given**: query ตรงจาก `C_PoolSlotTemplate` (ปรับจากภาคผนวก 9.B STEP 1–2) กรองเงื่อนไขเดียวกับที่ PROC ใช้ทุกจุด (SQL บรรทัด 275–280: `ProviderCode`, `StartTime`/`EndTime` NOT NULL, `PoolCode` ของสาขา 00006, `DeliveryOptionCode='DIY'`) แล้ว `GROUP BY (StartTime, EndTime)` รวม `SUM(Capacity)` เลียนแบบ `#setup_col` 5.1 (SQL บรรทัด 288–298)
- **When**: รัน PROC (หรือ query logic เทียบเท่า) กับ `PoolCode`/ช่วงวันเดียวกัน ดึงค่า `SetupQty` คอลัมน์ TOTAL ต่อ `(StartTime, EndTime)`
- **Then (ผ่าน)**: `SetupQty` ที่ PROC คำนวณ ต้องตรงกับผลรวม `SUM(Capacity)` ที่ query ตรงจาก `C_PoolSlotTemplate` **100% ทุกช่วงเวลา** (ไม่เทียบกับไฟล์ CFW อีกต่อไป — ไฟล์ `Result_..._Delivery.xlsx`/`RPT_UtilizationSlotDeliveryPickup.xlsx` ใช้แค่เป็น "เบาะแส" ว่าควรเช็คช่วงเวลาไหนก่อน เนื่องจากเคยพบตัวเลขต่างกันที่ store 00006, R29–R44)
- **Pass criteria**: ตรงกัน 100% ทุกช่วงเวลาที่มีเทียบ ไม่มีค่าใดต่างแม้ 1 หน่วย

**Unhappy Case — template ที่ `ChannelCode` ไม่ match กับ `M_ChannelOfSell` ที่ Active (channel กำพร้า)**
- **Given**: `SELECT * FROM C_PoolSlotTemplate t WHERE t.PoolCode=@PoolCode AND t.DeliveryOptionCode='DIY' AND t.ChannelCode IS NOT NULL AND NOT EXISTS (SELECT 1 FROM M_ChannelOfSell c WHERE c.ChannelCode=t.ChannelCode AND c.ProviderCode=t.ProviderCode AND c.IsActive=1 AND c.ShortName IS NOT NULL)` — นับ template ที่ระบุ `ChannelCode` แต่ไม่ match กับ channel ที่ยัง active (ต่างจาก NULL ChannelCode ที่ถูกจัดเข้า `SHARED` แล้วตาม SQL 5.3 บรรทัด 310–320)
- **When**: เทียบว่า Capacity ของ template กลุ่มนี้ถูกนับรวมใน `SetupQty` คอลัมน์ **TOTAL** หรือไม่ (5.1 ไม่กรอง ChannelCode จึงควรรวม) และถูกนับใน **คอลัมน์ channel รายตัว** หรือคอลัมน์ `SHARED` หรือไม่ (5.2/5.3 กรอง JOIN `#channel`/`ChannelCode IS NULL` เท่านั้น จึง**ไม่ครอบคลุม** เคส channel กำพร้านี้)
- **Then (ผ่าน — ตามที่ออกแบบไว้)**: จำนวนแถวกลุ่มนี้ที่ "หลุด" จากคอลัมน์ราย channel (ไม่ไปโผล่ที่ SD/WA/XB/XC และไม่ไปโผล่ที่ SHARED) แต่ **ยังคงอยู่ใน TOTAL** ต้อง = จำนวน record ที่ query เจอทั้งหมด (คือ "หลุดแบบตั้งใจ" ตามโครงสร้าง PROC ปัจจุบัน ไม่ใช่บั๊ก แต่เป็นช่องว่างของ design ที่ SHARED ไม่ครอบคลุม channel กำพร้า) — ต้องบันทึกจำนวนที่ query ได้แนบไว้เป็นหลักฐาน
- **Then (ไม่ผ่าน)**: ถ้าพบว่า Capacity กลุ่มนี้ **หายไปจาก TOTAL ด้วย** (ไม่ถูกนับที่ไหนเลย) → เป็นบั๊กจริงที่ต้องแก้ที่ query 5.1 ทันที (ไม่ใช่แค่ design gap)
- **Pass criteria**: `COUNT(channel กำพร้า)` ที่ query เจอ ต้องเท่ากับส่วนต่างระหว่าง (SetupQty TOTAL) กับ (SetupQty SD+WA+XB+XC+SHARED+VIP) ของช่วงเวลาเดียวกันพอดี — ถ้าตัวเลขไม่เท่ากันแปลว่ามี Capacity หายไปจริง (fail)

### AC สำหรับข้อ 3.3 — จำนวนแถวของ PROC ต้องตรงกับจำนวน (template × วัน) ใน DB

**Happy Case — Pool/สาขา Active ปกติ**
- **Given**: `SELECT COUNT(*) FROM C_PoolSlotTemplate WHERE PoolCode=@PoolCode AND DeliveryOptionCode='DIY' AND StartTime IS NOT NULL AND EndTime IS NOT NULL` (ต่อยอดภาคผนวก 9.B STEP 2)
- **When**: เทียบ `จำนวน template record ดังกล่าว × จำนวนวันในช่วง (DATEDIFF(DAY,@DtFrom,@DtTo)+1)` กับจำนวนแถวจริงที่ PROC output คืนมาสำหรับ Pool/สาขานั้น (ตาม logic CROSS JOIN #dates, SQL บรรทัด 384–401)
- **Then (ผ่าน)**: จำนวนแถว PROC output ต้อง = `template record × จำนวนวัน` พอดี 100% (ไม่เทียบ CFW export อีกต่อไป — ไฟล์ CFW ที่เคยพบต่างกัน 20 แถวใช้เป็นเบาะแสเท่านั้นว่าควรเช็คสาขา 00006 ก่อน)
- **Pass criteria**: สูตร `#แถว = #template × #วัน` ต้องลงตัวเป๊ะ

**Unhappy Case — สาขา Active แต่ Pool ไม่ Active หรือไม่มี Pool ผูกอยู่**
- **Given**: `SELECT pl.PlaceCode, pl.MechandiseCode, pl.MPoolId FROM M_Place pl WHERE pl.ProviderCode='CFW' AND pl.IsActive=1 AND pl.MechandiseCode IS NOT NULL AND (pl.MPoolId IS NULL OR NOT EXISTS (SELECT 1 FROM M_Pool po WHERE po.Id=pl.MPoolId AND po.IsActive=1))` — นับสาขาที่ Active แต่ไม่มี Pool ที่ Active ผูกอยู่ (จะทำให้สาขานั้นหายไปทั้งแถวจาก `#store`, SQL บรรทัด 208–225 เพราะ `JOIN M_Pool po ... AND po.IsActive=1`)
- **When**: เทียบจำนวนสาขาที่เจอในเงื่อนไขนี้ กับจำนวนสาขาที่ **ไม่ปรากฏเลยสักแถว** ใน PROC output (ทั้งที่เป็นสาขา Active)
- **Then (ผ่าน — ตามที่ออกแบบไว้)**: ทุกสาขาที่เจอในเงื่อนไขนี้ต้อง**หายไปจากรายงานทั้งหมด (0 แถว)** ตรงตาม design (สาขาไม่มี pool ที่ active = ไม่มี capacity มาแสดง จึงไม่ควรมีแถว) — นับจำนวนสาขากลุ่มนี้ไว้เป็น "จำนวนแถวที่หลุดออกจากรายงานโดยตั้งใจ" แจ้ง PO ว่ามีกี่สาขา (ถ้า >0 ต้องแจ้งว่าสาขาไหนบ้างเผื่อเป็นข้อมูล master ที่ควรแก้)
- **Then (ไม่ผ่าน)**: ถ้าพบสาขากลุ่มนี้มีแถวโผล่ในรายงานอยู่ (ไม่ควรเกิดตาม SQL logic ปัจจุบัน) → ต้องกลับไปตรวจ `#store`/`#setup` join อีกครั้ง เพราะขัดกับที่ SQL เขียนไว้
- **Pass criteria**: `จำนวนสาขาที่เข้าเงื่อนไข = จำนวนสาขา Active ที่หายไปจากรายงานทั้งหมด` ต้องเท่ากันเป๊ะ (เท่ากับ 0 ก็ถือว่าผ่าน แปลว่าไม่มีเคสนี้ในข้อมูลจริง)

### AC สำหรับข้อ 3.4 — แถว Usage>0 แต่ไม่มี Set Up (`IsMissingSetup`) ต้องไม่หายไปจากรายงาน

**Happy Case — booking ที่มี template รองรับครบ**
- **Given**: สุ่ม booking จาก `D_BookingLog` (`IsActive=1`) ที่มี template ใน `C_PoolSlotTemplate` รองรับตรงช่วงเวลา/channel พอดี
- **When**: เทียบว่า PROC output มีแถวของ (Store, SlotDay, SlotTime, ColumnKey) นั้น พร้อม `SetupQty>0` และ `UsageQty` ตรงกับจำนวน booking จริง
- **Then (ผ่าน)**: `UsageQty` ใน PROC = `COUNT(*)` จาก `D_BookingLog` ตรงเงื่อนไขเดียวกันทุกแถว 100%
- **Pass criteria**: ตรงกัน 100% ไม่มีผลต่าง

**Unhappy Case — booking ที่ไม่มี template รองรับเลย (`IsMissingSetup=1`)**
- **Given**: query ตรงจาก DB (ไม่ใช้ query ในภาคผนวก 9 เดิม — เป็น query ใหม่): `SELECT bl.PlaceCodeMerchandise_Send, CAST(bl.StartDate AS DATE) SlotDay, CAST(bl.StartDate AS TIME) StartTime, CAST(bl.EndDate AS TIME) EndTime, COUNT(*) AS UsageQty FROM D_BookingLog bl WHERE bl.ProviderCode='CFW' AND bl.IsActive=1 AND bl.DeliveryOptionCode='DIY' AND bl.StartDate>=@DtFrom AND bl.StartDate<@DtTo+1 AND NOT EXISTS (SELECT 1 FROM C_PoolSlotTemplate t JOIN M_Place pl ON pl.PoolCode... WHERE t.PoolCode=<pool ของสาขา bl> AND t.StartTime=CAST(bl.StartDate AS TIME) AND t.EndTime=CAST(bl.EndDate AS TIME)) GROUP BY ...` — นับ booking ที่ **ไม่มี template คู่กันเลย** จาก source ตรงๆ (แทนที่จะอ่านจากไฟล์ export)
- **When**: เทียบจำนวนแถว/จำนวน booking ที่ query เจอ กับจำนวนแถวใน PROC output ที่มี `IsMissingSetup=1` (SetupQty ว่าง, UsageQty>0) สำหรับ (Store, SlotDay, SlotTime, ColumnKey) เดียวกัน
- **Then (ผ่าน)**: จำนวนแถว/จำนวน booking ต้องตรงกัน **100%** (PROC ไม่ทำ booking กลุ่มนี้หายไปจากรายงานเลยสักตัว — ตาม design FULL OUTER JOIN ข้อสมมติ F, SQL บรรทัด 124, 386, 466–474) และค่าที่แสดงต้องเป็น `Utilization="0.00%"` ตามข้อสมมติ D (SQL บรรทัด 116–121) — เมื่อ query DB ยืนยันตัวเลขตรงกันแล้ว **ถึงจะเอาไปถามต่อ CFW/PO ว่ายอมรับ display "0.00%" แบบนี้หรือไม่** (คำถามเรื่อง UX ยังต้องถาม CFW ตามข้อ 6.B — แต่ "ข้อมูลไม่ตกหล่นจาก DB" ต้อง verify ด้วย query นี้ก่อนเป็นอันดับแรก)
- **Then (ไม่ผ่าน)**: ถ้าจำนวนที่ query เจอจาก DB **มากกว่า** จำนวนแถว `IsMissingSetup=1` ที่ PROC output คืนมา → แปลว่ามี booking บางส่วนหายไปจากรายงานจริง (บั๊ก) ต้องเปิด defect ทันที ไม่ใช่แค่ประเด็น display
- **Pass criteria**: `COUNT(booking ที่ไม่มี template จาก DB) = COUNT(แถว IsMissingSetup=1 ใน PROC output)` ต้องเท่ากันเป๊ะ ต่างกันแม้ 1 แถว = ไม่ผ่าน

### AC สำหรับข้อ 3.5 — Usage ของ VIP fallback (Usage>Setup) ต้องถูกนับครบจาก `D_BookingLog`

**Happy Case — VIP booking ที่มี VIP template รองรับ**
- **Given**: สุ่ม booking ที่ `D_BookingLog.SlotType` normalize เป็น 'VIP' และมี template `C_PoolSlotTemplate` ที่ `SlotType` normalize เป็น 'VIP' รองรับตรง Pool/เวลา (SQL 5.4 บรรทัด 322–328)
- **When**: เทียบ `SetupQty`/`UsageQty` คอลัมน์ VIP ที่ PROC คำนวณ กับผลรวมตรงจาก `C_PoolSlotTemplate`/`D_BookingLog`
- **Then (ผ่าน)**: ตรงกัน 100% ทั้ง Setup และ Usage
- **Pass criteria**: ตรงกัน 100%

**Unhappy Case — VIP booking ที่ fallback เข้า slot ทั่วไป (ไม่มี VIP template รองรับ, BR011)**
- **Given**: `SELECT bl.PlaceCodeMerchandise_Send, CAST(bl.StartDate AS DATE) SlotDay, CAST(bl.StartDate AS TIME) StartTime, CAST(bl.EndDate AS TIME) EndTime, COUNT(*) AS VipUsageQty FROM D_BookingLog bl WHERE bl.ProviderCode='CFW' AND bl.IsActive=1 AND UPPER(LTRIM(RTRIM(ISNULL(bl.SlotType,'')))) = 'VIP' AND bl.StartDate>=@DtFrom AND bl.StartDate<@DtTo+1 GROUP BY ...` เทียบกับ `SELECT ... FROM C_PoolSlotTemplate t WHERE UPPER(LTRIM(RTRIM(ISNULL(t.SlotType,'')))) = 'VIP'` (ไม่มี VIP template คู่กันในเวลาเดียวกัน = fallback) — เป็น query ใหม่ ต่อยอดจากภาคผนวก 9.B STEP 3 (ที่เดิมเช็คเฉพาะ R53) ให้ขยายเป็นเช็คทุกแถวที่มี VIP usage ไม่ใช่แค่ 1 แถวตัวอย่าง
- **When**: เทียบผลรวม `VipUsageQty` ต่อ (Store, SlotDay, SlotTime) ที่ query ตรงจาก `D_BookingLog` กับค่า `UsageQty` คอลัมน์ VIP ที่ PROC output คืนมา และเทียบว่า `Utilization TOTAL` ของแถวนั้นคำนวณจาก `(Usage channel ปกติ + VIP Usage) / SetUp channel ที่ VIP ไปยืมใช้` ตรงตามที่พบจริง (R53: 4/1=400%)
- **Then (ผ่าน)**: `UsageQty` คอลัมน์ VIP ของ PROC = `VipUsageQty` จาก DB **100% ทุกแถว** (ไม่มี VIP booking หายไปจากรายงาน แม้จะ fallback ก็ตาม) — Utilization ที่คำนวณได้ >100% ถือเป็นค่าที่ **ถูกต้องตาม design** (ไม่ cap, ไม่ error) เมื่อ query ยืนยันตัวเลข usage ตรงกับ DB แล้ว
- **Then (ไม่ผ่าน)**: `UsageQty` คอลัมน์ VIP ของ PROC น้อยกว่า `VipUsageQty` จาก DB (มี VIP booking บางส่วนหายไปจากรายงาน) → เป็นบั๊กจริง ต้องเปิด defect ทันที (ไม่ใช่แค่ประเด็น "ควร cap ที่ 100% หรือไม่" อีกต่อไป)
- **Pass criteria**: `SUM(UsageQty คอลัมน์ VIP จาก PROC) = SUM(VipUsageQty จาก DB)` ต้องเท่ากันทุกแถวที่เทียบได้ 100%

### AC สำหรับข้อ 3.7 — ไม่มี Sale Source "SD"/VIP ใน template ฝั่ง Pickup จริงหรือไม่

**Happy Case — template PIC ของ channel ที่มีอยู่จริง (WA/XB/XC)**
- **Given**: `SELECT * FROM C_PoolSlotTemplate WHERE DeliveryOptionCode='PIC' AND ChannelCode IN (SELECT ChannelCode FROM M_ChannelOfSell WHERE ProviderCode='CFW' AND IsActive=1 AND ShortName IN ('WA','XB','XC'))`
- **When**: เทียบว่า PROC (รันด้วย `@DeliveryOptionCode='PIC'`) สร้างคอลัมน์ WA/XB/XC พร้อม SetupQty ตรงกับผลรวม Capacity จาก query นี้
- **Then (ผ่าน)**: ตรงกัน 100%
- **Pass criteria**: ตรงกัน 100%

**Unhappy Case — template PIC ของ SD หรือ VIP (เช็คว่ามีจริงหรือไม่)**
- **Given**: `SELECT COUNT(*) FROM C_PoolSlotTemplate t WHERE t.ProviderCode='CFW' AND t.DeliveryOptionCode='PIC' AND (t.ChannelCode IN (SELECT ChannelCode FROM M_ChannelOfSell WHERE ProviderCode='CFW' AND ShortName='SD' AND IsActive=1) OR UPPER(LTRIM(RTRIM(ISNULL(t.SlotType,'')))) = 'VIP')` — เป็น query ใหม่ นับ template PIC ของ SD/VIP ตรงๆ จาก DB (แทนที่จะดูจากโครงสร้างคอลัมน์ในไฟล์ CFW Pickup อีกต่อไป)
- **When**: เทียบจำนวน record ที่ query เจอ กับการมี/ไม่มีคอลัมน์ SD และกลุ่ม VIP ใน PROC output เมื่อรันด้วย `@DeliveryOptionCode='PIC'`
- **Then (ผ่าน — ไม่มีเคสนี้จริง)**: `COUNT(*) = 0` (ไม่มี template PIC ของ SD/VIP อยู่ใน DB เลย) → ยืนยันว่า PROC ไม่แสดงคอลัมน์ SD/VIP สำหรับ Pickup เพราะ**ไม่มีข้อมูลจริง** (ถูกต้องตาม design, ไม่ใช่บั๊ก dynamic-hide) ปิดข้อนี้
- **Then (ไม่ผ่าน — มีเคสนี้จริงแต่หาย)**: `COUNT(*) > 0` แต่ PROC output (รันจริงหรือ query เทียบเท่า) **ไม่สร้างคอลัมน์ SD/VIP ออกมา** → เป็นบั๊กจริงที่ query 5.2/5.4 (SQL บรรทัด 300–328) ไม่ครอบคลุม `DeliveryOptionCode='PIC'` ต้องแก้ทันที — ห้ามปิดข้อนี้
- **Pass criteria**: `COUNT(*)=0` → ผ่านทันที; `COUNT(*)>0` → ต้องเห็นคอลัมน์ SD/VIP ปรากฏใน PROC output ครบตามจำนวนที่ query เจอ จึงจะถือว่าผ่าน

### AC สำหรับข้อ 3.8 — ผลลัพธ์ PROC ฝั่ง Pickup (`@DeliveryOptionCode='PIC'`) ต้อง verify กับ DB ได้เอง โดยไม่ต้องรอไฟล์ CFW

**Happy Case**
- **Given**: รัน PROC จริง (หรือ query เทียบเท่า) ด้วย `@DeliveryOptionCode='PIC'` ช่วงวันที่ 01–10/09/2026 ทุกสาขา
- **When**: ใช้วิธีเดียวกับ AC ข้อ 3.1/3.3/3.5 (เทียบ SetupQty/UsageQty/จำนวนแถว กับ `C_PoolSlotTemplate`/`D_BookingLog` ที่กรอง `DeliveryOptionCode='PIC'` ตรงๆ)
- **Then (ผ่าน)**: ตัวเลขทุกจุดตรงกับ DB 100% เหมือนที่ต้องผ่านในข้อ 3.1/3.3/3.5 ฝั่ง Delivery — **ไม่จำเป็นต้องรอไฟล์ TMS PROC output ฝั่ง Pickup หรือไฟล์ `Result_..._Pickup.xlsx` มาเทียบอีกต่อไป** เพราะเกณฑ์หลักคือ DB ไม่ใช่ไฟล์ export (ไฟล์ CFW Pickup ใช้เป็นแค่ข้อมูลอ้างอิงว่าโครงสร้างคอลัมน์หน้าตาประมาณไหน)
- **Pass criteria**: เหมือน AC 3.1/3.3/3.5 (ตรง 100%) แต่ scope เป็น `DeliveryOptionCode='PIC'`

**Unhappy Case — ผลรวมข้ามฝั่ง Delivery/Pickup ของ booking เดียวกัน (ผูก `DeliveryOptionCode` ผิดฝั่ง)**
- **Given**: `SELECT bl.* FROM D_BookingLog bl WHERE bl.ProviderCode='CFW' AND bl.IsActive=1 AND bl.DeliveryOptionCode NOT IN ('DIY','PIC')` — เป็น query ใหม่ เช็คว่ามี booking ที่ `DeliveryOptionCode` เป็นค่าอื่น/NULL/พิมพ์ผิด หลุดจากทั้งสองฝั่งหรือไม่ (PROC filter `@DeliveryOptionCode IS NULL OR bl.DeliveryOptionCode=@DeliveryOptionCode`, SQL บรรทัด 357 — ถ้ารันแยกทีละฝั่ง DIY/PIC ค่าที่ไม่ตรงทั้งคู่จะไม่ถูกนับที่ไหนเลย)
- **When**: เทียบจำนวน booking กลุ่มนี้ กับผลรวม `UsageQty` ของรายงานทั้งสองฝั่ง (DIY-run + PIC-run) รวมกัน เทียบกับ `COUNT(*)` ทั้งหมดของ `D_BookingLog` (`IsActive=1`, ช่วงวันเดียวกัน ไม่กรอง `DeliveryOptionCode`)
- **Then (ผ่าน)**: `COUNT(DeliveryOptionCode ที่ไม่ใช่ DIY/PIC) = 0` → ไม่มี booking หลุดจากทั้งสองฝั่ง ปิดข้อนี้ได้เมื่อรวมกับผล Happy Case ข้างต้น
- **Then (ไม่ผ่าน)**: `COUNT(...) > 0` → มี booking ที่ไม่ถูกนับในรายงานฝั่งไหนเลย ต้องแจ้ง PO/CFW ว่าต้องนิยาม `DeliveryOptionCode` ที่ผิดปกติเหล่านี้ว่าควรจัดเข้าฝั่งไหน หรือเป็น data quality issue ที่ต้องแก้ต้นทาง
- **Pass criteria**: `COUNT(*) = 0` จึงถือว่าผ่านแบบไม่มีข้อโต้แย้ง

### AC สำหรับข้อ 3.20 — ข้อจำกัดกระบวนการตรวจสอบ: ทุกข้อ High ต้องปิดด้วยผล query DB เท่านั้น

**Happy Case**
- **Given**: รันชุด query ทั้งหมดที่อ้างถึงในหมวด 8 นี้ (ทั้งที่ต่อยอดจากภาคผนวก ข้อ 9 เดิม และ query ใหม่ที่เขียนกำกับไว้ในแต่ละ AC) ต่อ DB จริง
- **When**: นำผลลัพธ์แต่ละ query มาเทียบกับ Pass criteria ของ AC ข้อ 3.1 / 3.3 / 3.4 / 3.5 / 3.7 / 3.8 / 3.21 ทีละข้อ (ทั้ง Happy และ Unhappy Case)
- **Then (ผ่าน)**: ทั้ง 7 ข้อมีผล query DB ที่สรุป pass/fail ได้ชัดเจนครบทั้ง Happy และ Unhappy Case (14 เคสย่อยรวม) ไม่มีข้อไหนค้างเป็น "ฟันธงไม่ได้" — **ไม่นับว่าปิดด้วยการรอไฟล์ CFW เพิ่มอีกต่อไป** ปิดข้อ 3.20 ได้ไม่ว่าผลลัพธ์แต่ละข้อย่อยจะ pass หรือ fail (เป้าหมายคือ "มีข้อมูล DB มายืนยันครบ" ไม่ใช่ "ทุกข้อต้อง pass")
- **Pass criteria**: 7/7 ข้อ (Happy+Unhappy ครบทั้งคู่ต่อข้อ) ต้องมีผลจาก DB query มายืนยันได้

**Unhappy Case — DB ไม่มีข้อมูลย้อนหลังให้ query (เช่น ไม่มี audit/history table)**
- **Given**: พยายาม query capacity/booking ย้อนหลัง ณ ช่วงเวลาที่สร้างไฟล์ `Result_..._Delivery.xlsx`/`RPT_UtilizationSlotDeliveryPickup.xlsx` แต่ตาราง `C_PoolSlotTemplate` เก็บแค่ค่าปัจจุบัน (ไม่มี effective-date/history)
- **When**: เทียบว่าค่าปัจจุบันจาก DB อธิบายผลต่างที่เคยพบในไฟล์ export ได้หรือไม่ (เช่น AC 3.1)
- **Then (ผ่าน)**: ถ้าค่าปัจจุบันจาก DB ตรงกับไฟล์ใดไฟล์หนึ่ง (TMS หรือ CFW) ให้ถือว่าปิดได้โดยสรุปว่าอีกไฟล์เป็น snapshot เก่ากว่า — ไม่ต้องมี history table ก็ปิดได้ถ้าตรงกับฝั่งใดฝั่งหนึ่งชัดเจน
- **Then (ไม่ผ่าน)**: ค่าปัจจุบันจาก DB ไม่ตรงกับทั้งสองไฟล์เลย และไม่มี history/audit ให้ย้อนดู → ต้อง escalate ขอ log อื่น (เช่น application log ของ `BookingService`, deployment history ของ template) ไม่ปิด checklist จนกว่าจะหาทางยืนยันได้
- **Pass criteria**: มีคำตอบอย่างใดอย่างหนึ่งชัดเจน (ปิดได้ด้วยเหตุผล หรือ escalate พร้อมระบุว่าต้องการข้อมูล/สิทธิ์อะไรเพิ่ม)

### AC สำหรับข้อ 3.21 — Usage>100% กับกรณี Share Slot (Pool sharing) ต้อง verify จาก `D_BookingLog`/`C_PoolSlotTemplate` โดยตรง

**Happy Case — Pool ที่มีสาขาเดียว (StoreCountInPool=1) หรือ Pool ที่แชร์กันแต่ไม่มี VIP fallback**
- **Given**: รัน query ภาคผนวก 9.A ข้อ 1 หา Pool ทั้งหมด (`StoreCountInPool` ทุกค่า) แล้ว query ข้อ 2 ดึง Usage ต่อสาขา/วัน/สโลต เทียบกับ SetUp ของ Pool นั้น
- **When**: กรองเฉพาะแถวที่ **ไม่ใช่** VIP fallback (`SlotType` ปกติ) เทียบ Usage ต่อสาขา กับ SetUp ต่อ Pool
- **Then (ผ่าน)**: ทุกแถวกลุ่มนี้ Usage ≤ SetUp เสมอ (ไม่ว่า Pool จะมีสาขาเดียวหรือหลายสาขา)
- **Pass criteria**: 0 แถวที่ Usage>SetUp ในกลุ่มนี้

**Unhappy Case — Pool ที่แชร์กัน (`StoreCountInPool>1`) และมีการจองรวมกันเกิน capacity ของ Pool**
- **Given**: ต่อยอด query ภาคผนวก 9.A ข้อ 1–2 (หา Pool ที่ `StoreCountInPool>1` แล้วดึง Usage ราย SlotDay/SlotTime ของทุกสาขาในพูลนั้น พร้อม `SlotType` จาก `D_BookingLog`)
- **When**: (1) เทียบ Usage **ต่อสาขาเดียว** กับ SetUp ของ Pool หาแถวที่ Usage (ต่อสาขา, ไม่ใช่ VIP) > SetUp ของ Pool — (2) คู่ขนาน: `SUM(Usage ของทุกสาขาในพูล)` ต่อ (SlotDay, SlotTime) เทียบกับ SetUp ของ Pool เดียวกัน (ค่าเดียว ไม่บวกซ้ำ) หาแถวที่ผลรวมทุกสาขา > SetUp ทั้งที่แต่ละสาขาเดี่ยวๆ ยังต่ำกว่า 100%
- **Then (ผ่าน)**: (1) ไม่พบแถวใดที่ Usage ต่อสาขา (ไม่ใช่ VIP) > SetUp ต่อ Pool เลย → สรุปคำตอบให้ PO ได้ว่า **"pool sharing เองไม่ทำให้เกิด Usage>100% ต่อแถวเพิ่มเติมนอกเหนือจาก VIP fallback ที่รู้อยู่แล้ว (ข้อ 3.5)"**
- **Then (ไม่ผ่าน — เคสที่ 1)**: พบแถวที่ Usage ต่อสาขา (ไม่ใช่ VIP) > SetUp ต่อ Pool อย่างน้อย 1 แถว → คำตอบเปลี่ยนเป็น **"pool sharing ทำให้เกิด Usage>100% ได้จริงแม้ไม่มี VIP fallback"** ต้องแจ้ง PO ทันที
- **Then (ไม่ผ่าน — เคสที่ 2, under-report)**: พบแถวที่ `SUM(Usage ทุกสาขาในพูล) > SetUp ของพูล` แต่ทุกแถวรายสาขายังโชว์ <100% (เพราะ SetUp ถูกนับซ้ำเต็มจำนวนไม่ได้หารตามสัดส่วน, SQL บรรทัด 398–401) → ต้องบันทึกเป็นความเสี่ยง "under-report" แยกออกมา แจ้ง PO เพิ่มเติมนอกเหนือจากคำถามเดิม (ไม่ใช่คำตอบ "ไม่มีเคสนี้" แบบเต็มปาก)
- **Pass criteria**: เคสที่ 1 ต้อง = 0 แถว (Usage ต่อสาขา ไม่ใช่ VIP > SetUp ต่อ Pool) จึงถือว่าผ่านหลัก, เคสที่ 2 (under-report) นับแยกเป็นข้อสังเกตประกอบเสมอไม่ว่าเคสที่ 1 จะผ่านหรือไม่

## 9. ภาคผนวก: ร่าง SQL Query สำหรับ DBA/ทีมที่มีสิทธิ์เข้าถึง DB (ยังไม่ได้ execute)

> **หมายเหตุสำคัญ:** session นี้ไม่มีเครื่องมือเชื่อมต่อ database ใดๆ จึง **รัน query เหล่านี้เองไม่ได้** — query ด้านล่างร่างจาก schema/table/column ที่ปรากฏในตัว `PROC_RPT_UtilizationSlotDeliveryPickup.sql` เท่านั้น (ยังไม่ผ่านการทดสอบรันจริง) กรุณาให้ DBA หรือผู้มีสิทธิ์เข้าถึง DB ตรวจสอบชื่อ table/column ให้ตรงกับ schema จริงก่อนรัน โดยเฉพาะค่าพารามิเตอร์ `ProviderCode='CFW'` และ `@PoolCode` ที่ต้องแทนค่าจริงจาก STEP 1 ก่อน

### 9.A ตรวจ Pool sharing (StoreCountInPool) — ใช้ตอบข้อ 3.12, 3.18, 3.21

```sql
-- 1) หา Pool ที่มีมากกว่า 1 สาขาใช้ capacity ร่วมกัน (StoreCountInPool > 1)
SELECT
    po.PoolCode,
    COUNT(*) AS StoreCountInPool,
    STRING_AGG(pl.PlaceCode + ' (' + ISNULL(pl.NameLocal, pl.BranchName) + ')', ', ')
        WITHIN GROUP (ORDER BY pl.PlaceCode) AS StoresInPool
FROM M_Place pl
JOIN M_Pool po ON po.Id = pl.MPoolId AND po.IsActive = 1
WHERE pl.ProviderCode = 'CFW'
  AND pl.IsActive = 1
  AND pl.MechandiseCode IS NOT NULL
GROUP BY po.PoolCode
HAVING COUNT(*) > 1
ORDER BY COUNT(*) DESC;

-- 2) สำหรับ Pool ที่เจอในข้อ 1 (แทน @PoolCode ด้วยค่าจริง) ดู Usage ของแต่ละสาขาในพูลนั้น
--    เทียบกับ Set Up ของพูล เพื่อดูว่าสาขาใดสาขาหนึ่ง Usage เกิน SetUp ของพูลหรือไม่ (ตอบข้อ 3.21)
SELECT
    pl.PlaceCode, pl.MechandiseCode, pl.NameLocal,
    CAST(bl.StartDate AS DATE) AS SlotDay,
    CAST(bl.StartDate AS TIME) AS StartTime,
    CAST(bl.EndDate   AS TIME) AS EndTime,
    COUNT(*) AS UsageQty
FROM TMSSlotBooking.dbo.D_BookingLog bl
JOIN M_Place pl ON pl.MechandiseCode = bl.PlaceCodeMerchandise_Send AND pl.ProviderCode = bl.ProviderCode
JOIN M_Pool  po ON po.Id = pl.MPoolId
WHERE bl.ProviderCode = 'CFW'
  AND bl.IsActive = 1
  AND po.PoolCode = @PoolCode          -- แทนค่าจาก query ข้อ 1
  AND bl.StartDate >= '2026-09-01' AND bl.StartDate < '2026-09-11'
GROUP BY pl.PlaceCode, pl.MechandiseCode, pl.NameLocal,
         CAST(bl.StartDate AS DATE), CAST(bl.StartDate AS TIME), CAST(bl.EndDate AS TIME)
ORDER BY pl.PlaceCode, SlotDay, StartTime;
```

### 9.B ตรวจตัวเลข Set Up ไม่ตรงกัน (Store 00006) — ใช้ตอบข้อ 3.1, 3.3, 3.20

```sql
-- STEP 1: หา PoolCode ของสาขา 00006
SELECT pl.PlaceCode, pl.MechandiseCode, pl.MPoolId, po.PoolCode
FROM M_Place pl
JOIN M_Pool po ON po.Id = pl.MPoolId
WHERE pl.MechandiseCode = '00006'
  AND pl.ProviderCode = 'CFW'
  AND pl.IsActive = 1;

-- STEP 2: ดู capacity template ทั้งหมดของ pool นั้น (ช่วงวันที่ 01-03/09/2026 ที่พบตัวเลขต่างกัน)
SELECT PoolCode, DeliveryOptionCode, ChannelCode, SlotType, StartTime, EndTime, Capacity
FROM C_PoolSlotTemplate
WHERE ProviderCode = 'CFW'
  AND PoolCode = @PoolCode             -- แทนค่าจาก STEP 1
  AND DeliveryOptionCode = 'DIY'
ORDER BY StartTime, EndTime;
-- เทียบจำนวน record และผลรวม Capacity กับตัวเลขที่เห็นในไฟล์ TMS PROC output (SetUp 3,2,2,2,2,_,2,_,1)
-- และไฟล์ CFW Delivery (SetUp 9,9,6,6,3,_,6,_,3) ว่าตรงกับฝั่งไหน หรือไม่ตรงทั้งคู่ (แปลว่าเป็นคนละ snapshot)

-- STEP 3: ยืนยันจำนวน VIP usage จริงของแถว R53 (SlotTime 17:00-18:00, 2026-09-03) ที่ Utilization เกิน 100%
SELECT bl.*
FROM TMSSlotBooking.dbo.D_BookingLog bl
WHERE bl.ProviderCode = 'CFW'
  AND bl.IsActive = 1
  AND bl.PlaceCodeMerchandise_Send = '00006'
  AND bl.DeliveryOptionCode = 'DIY'
  AND CAST(bl.StartDate AS DATE) = '2026-09-03'
  AND CAST(bl.StartDate AS TIME) = '17:00:00';
```
