# วัตถุประสงค์ของ Skill นี้

เขียน Acceptance Criteria ที่**ครอบคลุม Happy Case แบบละเอียดที่สุด** (เพราะ PO ต้องเข้าไปช่วย QA เทสต์ส่วนนี้เองบ่อยๆ) และมี Edge Case ประกอบพอสมควร แต่ไม่ต้องลึกเท่า Happy Case

ต่างจาก AC section ใน ba2-tech-analyst ตรงที่ skill นี้**เจาะเฉพาะการเขียน AC ให้ทดสอบได้จริงแบบ step-by-step** ที่คนไม่ใช่ QA มืออาชีพ (เช่น PO) ก็หยิบไปกดทดสอบเองได้ทันที ไม่ต้องตีความเพิ่ม

---

# หลักการเขียน AC ที่ดี (ใช้เสมอ)

1. **เขียนแบบ Given–When–Then** ทุกข้อ ไม่เขียนแบบบรรยายกว้างๆ
2. **1 AC = 1 สิ่งที่ทดสอบได้จบในตัวเอง** ห้ามรวมหลาย assertion ไว้ในข้อเดียว
3. **ระบุผลลัพธ์ที่สังเกตได้จริงบนหน้าจอ** (เช่น "ขึ้นข้อความ 'บันทึกสำเร็จ'" ไม่ใช่ "ระบบทำงานถูกต้อง")
4. **เรียงลำดับตาม flow การใช้งานจริง** ไม่ใช่เรียงตามความซับซ้อนทางเทคนิค เพื่อให้ผู้ทดสอบไล่ตามได้เป็นขั้นเป็นตอน

## ⚠️ กฎเหล็ก: สลับมุมมองกลับมาเป็น "Business User" ก่อนเขียน AC

ก่อนเขียน AC ทุกครั้ง ให้ตัดภาพความคิดแบบ technical/API/automation ที่เพิ่งวิเคราะห์มาออกไปก่อน แล้วถามตัวเองว่า **"ถ้าฉันเป็น user ที่ไม่รู้เรื่องระบบข้างหลังเลย จะเห็นอะไร"**

**ห้ามเขียน AC ที่มีลักษณะต่อไปนี้ (ถือว่าหลุดจาก scope):**
- อธิบายว่าระบบ automate/ประมวลผลอะไรอยู่เบื้องหลัง (เช่น "ระบบเรียก API sync ข้อมูลไปยังระบบ X" ❌)
- อ้างอิงชื่อ endpoint, table, field ในฐานข้อมูล, หรือ implementation detail ใดๆ
- ใช้คำว่า "ระบบจะ trigger...", "background job จะ...", "ระบบจะ validate ผ่าน service..."
- ทดสอบ logic ระดับ code/unit test แทนที่จะทดสอบ behavior ที่ user เจอจริง

**ให้เขียนแทนด้วยสิ่งที่ user เห็น/ทำได้จริงบนหน้าจอเท่านั้น** เช่น:
```
❌ ผิด scope: Given ผู้ใช้กด submit When ระบบเรียก API POST /orders สำเร็จ Then background job อัปเดตสถานะใน DB

✅ ถูกต้อง: Given ผู้ใช้กรอกฟอร์มครบ When กดปุ่ม "บันทึก" Then หน้าจอแสดงข้อความ "บันทึกสำเร็จ" และสถานะในรายการเปลี่ยนเป็น "รอดำเนินการ"
```

รายละเอียด technical/automation เป็นสิ่งที่**เดฟใช้เองตอน implement** ไม่ใช่สิ่งที่ต้องอยู่ใน AC — AC มีไว้ให้คนที่ไม่ต้องรู้เทคนิค (เช่น PO, QA) ทดสอบได้เลย

# โครงสร้างการเขียน AC (สัดส่วนที่ต้องยึดตาม)

### ส่วนที่ 1 — Happy Case (สัดส่วนหลัก ~70% ของ AC ทั้งหมด)
ครอบคลุมทุก step ของ flow หลักที่ user ใช้งานแบบไม่มีข้อผิดพลาด โดยแตกละเอียดเป็นราย step ไม่รวบเป็นข้อใหญ่ข้อเดียว:

- ทุก field ที่ต้องกรอก/แสดงผล → มี AC แยกว่ากรอกถูกแล้วต้องเกิดอะไร
- ทุก action หลัก (submit, approve, cancel, search, filter) → มี AC แยกทีละ action
- ทุก role ที่เกี่ยวข้อง → ต้องมี Happy Case แยกตาม role ถ้าพฤติกรรมต่างกัน
- ผลลัพธ์สุดท้ายของ flow (เช่น สถานะเปลี่ยน, ข้อมูลถูกบันทึก, แจ้งเตือนถูกส่ง) → ต้องมี AC ยืนยันจุดจบของ flow ชัดเจน

**ตัวอย่างการแตกละเอียด (ห้ามรวบ):**
```
❌ ไม่ดี: Given ผู้ใช้กรอกฟอร์มครบ When กด submit Then ระบบทำงานถูกต้อง

✅ ดี:
- Given ผู้ใช้กรอกฟอร์มครบทุก field ที่จำเป็น
  When กดปุ่ม "บันทึก"
  Then ระบบแสดงข้อความ "บันทึกสำเร็จ" และ redirect ไปหน้ารายการ

- Given รายการถูกบันทึกสำเร็จแล้ว
  When ผู้ใช้กลับมาที่หน้ารายการ
  Then ต้องเห็นรายการที่เพิ่งบันทึกอยู่บนสุด พร้อมสถานะ "รอดำเนินการ"

- Given ผู้ใช้ role ผู้อนุมัติเข้าดูรายการนี้
  When กดปุ่ม "อนุมัติ"
  Then สถานะเปลี่ยนเป็น "อนุมัติแล้ว" และผู้ขอเห็นการแจ้งเตือน
```

### ส่วนที่ 2 — Edge Case สำคัญ (สัดส่วนรอง ~30%)
เลือกเฉพาะ edge case ที่**มีโอกาสเกิดจริงสูง** หรือกระทบ business rule โดยตรง ไม่ต้องครอบคลุมทุกกรณีที่เป็นไปได้ทางทฤษฎี:
- กรอกข้อมูลไม่ครบ / ผิดรูปแบบ
- สิทธิ์ไม่พอ (role ที่ไม่ควรทำ action นั้นได้)
- ข้อมูลซ้ำ/ชนกัน (เช่น อนุมัติซ้ำ)
- กรณีที่ business rule จาก BA1 ระบุไว้เป็นเงื่อนไขพิเศษ

# Checklist ก่อนส่ง AC ออกไป

ก่อนจบงานทุกครั้ง เช็คว่า:
- [ ] ทุก step ใน Happy Case ทดสอบแล้ว "รู้ผลลัพธ์ที่ควรเห็นบนจอ" ชัดเจน ไม่ต้องเดา
- [ ] ไล่ตาม AC ตั้งแต่ข้อแรกถึงข้อสุดท้ายแล้ว ครบ flow จริงหรือไม่ (ลองสวมบทบาทเป็นคนกดทดสอบเอง)
- [ ] ไม่มี AC ข้อไหนที่ใช้คำกว้างๆ ที่ทดสอบ pass/fail ไม่ได้ (เช่น "ทำงานได้ดี", "แสดงผลถูกต้อง")
- [ ] Edge case ที่เลือกมามีเหตุผลรองรับ ไม่ใช่ใส่ไปเรื่อยเพื่อความครบ

# Output Format

```markdown
## Acceptance Criteria: [ชื่องาน]

### Happy Case
1. Given ... When ... Then ...
2. Given ... When ... Then ...
...

### Edge Case ที่สำคัญ
1. Given ... When ... Then ...
...

### 📝 หมายเหตุสำหรับ PO ตอนช่วยทดสอบ
- ลำดับที่แนะนำให้ทดสอบก่อน-หลัง (ถ้ามี dependency ระหว่าง step)
- จุดที่ต้องเตรียมข้อมูลทดสอบล่วงหน้า (เช่น ต้องมี user role ไหนพร้อมก่อน)
```

# กติกาสำคัญ

0. **ก่อนเขียน AC เต็มรูปแบบ เช็คก่อนว่ารู้ครบทุก field/action/role บนหน้าจอที่เกี่ยวข้องหรือยัง** — ถ้าข้อมูลจาก Step 2/3 ของ ba2-tech-analyst ยังไม่ครบพอจะเขียน Happy Case ได้ครบ ให้ถามกลับก่อนเขียน ไม่เขียนไปก่อนแล้วมาแก้ทีหลัง (เสีย token)
1. **Happy Case ต้องแตกละเอียดพอที่ PO หยิบไปกดทดสอบเองได้ทันที** โดยไม่ต้องถามใครเพิ่ม — นี่คือเป้าหมายหลักของ skill นี้
2. ห้ามเขียน AC ที่ผลลัพธ์ "ตีความได้หลายแบบ" — ต้องระบุสิ่งที่เห็นบนจอแบบเจาะจง
3. ถ้า flow มีหลาย role ต้อง Happy Case แยกตาม role ให้ครบ ไม่รวบเป็นข้อเดียวแล้วสมมติว่าทุก role เหมือนกัน
4. ไม่ต้องพยายามครอบคลุม edge case ทุกกรณีทางทฤษฎี — เลือกเฉพาะที่มีโอกาสเกิดจริงหรือกระทบ business rule ชัดเจน
